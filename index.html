OWASP TOP 10:2025 · A02

Security Misconfiguration

A secure feature can still become vulnerable when its runtime, platform, cloud permissions, or operational defaults are wrong.

CORE DEFINITION

Security misconfiguration is a system, application, or cloud service configured incorrectly from a security perspective, creating an exploitable condition.

secure component + unsafe configuration = vulnerable deployment
PREVALENCE100%

of tested applications had some form of misconfiguration in the OWASP 2025 dataset.

ROOT CAUSEDrift

Manual changes and environment differences erode the reviewed baseline.

BEST LEVERAutomation

Build, verify, and continuously compare systems against a versioned secure baseline.

CLICK TO EXPLAIN

How A02 appears in real systems

Each pattern includes the exploit path, root cause, primary control, and useful evidence.

01Missing hardening+

Failure: default runtime settings expose unnecessary behavior.

Attack: enumerate services, endpoints, methods, banners, or sample apps that should not exist in production.

Defend: minimal images, approved baselines, immutable deployment, CIS-aligned checks.

Evidence → versioned baseline + passing configuration test
02Unnecessary features+

Failure: debug routes, consoles, sample apps, packages, accounts, or network listeners remain enabled.

Attack: use a forgotten surface with weaker controls than the main application.

Defend: least functionality; remove rather than merely hide.

Evidence → port inventory + route inventory + image SBOM
03Default credentials+

Failure: shipped usernames, passwords, API keys, or setup tokens are unchanged.

Attack: authenticate through an exposed administrative interface using public defaults.

Defend: disable defaults, force one-time enrollment, prefer federation and short-lived identity.

Evidence → no default principal accepted after bootstrap
04Verbose errors+

Failure: clients receive stack traces, file paths, queries, package versions, or internal hostnames.

Attack: trigger invalid input, then use leaked context to refine a later attack.

Defend: generic external response; detailed correlated log internally.

Evidence → response has error_id, not internal exception detail
05Missing security headers+

Failure: browser security directives are missing or overly permissive.

Attack: exploit another weakness with fewer browser-side constraints.

Defend: CSP, HSTS, frame-ancestors, nosniff, and secure cookie attributes selected for the application.

Evidence → automated header assertions on every environment
06Public cloud resources+

Failure: object storage, databases, snapshots, queues, or management endpoints accept unintended public access.

Attack: enumerate a reachable resource and read or modify exposed data.

Defend: block-public-access controls, private networking, least-privilege IAM, policy-as-code.

Evidence → effective policy test, not a console screenshot
07Container / Kubernetes gaps+

Failure: privileged mode, host mounts, root execution, broad RBAC, or open services collapse isolation.

Attack: turn an application compromise into node, cluster, or lateral access.

Defend: Pod Security Standards, admission policy, NetworkPolicy, restricted service accounts.

Evidence → rejected unsafe manifest + runtime posture telemetry
08Insecure secret placement+

Failure: long-lived keys are embedded in code, images, configuration, environment output, or pipelines.

Attack: retrieve leaked material and authenticate outside the intended workload.

Defend: workload identity, short-lived credentials, managed secret stores, rotation.

Evidence → no static cloud key in deployable artifact

OWASP TOP 10:2025 · A05

Injection

Injection happens when untrusted data reaches an interpreter and changes the meaning of a command, query, expression, or rendered document.

UNTRUSTED DATArequest parameter' OR '1'='1
+
COMMAND STRUCTUREdynamic query"… WHERE id='" + input
→
INTERPRETERchanges program meaningdatabase · shell · browser
→
IMPACTunauthorized actionread · modify · execute
PRIMARY RULE

Keep data separate from commands and queries.

Parameterization changes the interface: the interpreter receives command structure and data through separate channels. Validation alone is not the complete defense.

CLICK TO EXPLAIN

One concept, many interpreters

The syntax changes; the trust-boundary failure stays the same.

01SQL injection+

Interpreter: relational database.

Failure: input is concatenated into SQL structure.

Impact: authentication bypass, data disclosure, modification, deletion.

Primary defense: prepared statements / parameterized queries.

02NoSQL injection+

Interpreter: document or key-value query engine.

Failure: attacker-controlled operators or query objects are accepted.

Impact: filter bypass or unintended record access.

Primary defense: typed input schema, allow-listed fields, safe driver API.

03OS command injection+

Interpreter: operating-system shell.

Failure: a string containing input is executed through a shell.

Impact: arbitrary commands under the application identity.

Primary defense: avoid the shell; call a safe library or executable with an argument array.

04ORM / HQL injection+

Interpreter: ORM query language.

Failure: trusting a framework while still concatenating query fragments.

Impact: filter bypass and unauthorized data access.

Primary defense: bound parameters and constrained query builders.

05LDAP injection+

Interpreter: LDAP directory search filter.

Failure: unescaped input changes filter logic.

Impact: authentication bypass or directory disclosure.

Primary defense: safe directory APIs and LDAP-filter encoding.

06XSS+

Interpreter: browser HTML / JavaScript parser.

Failure: untrusted data is inserted into an executable output context.

Impact: actions in a victim's browser, data access, UI manipulation.

Primary defense: context-aware output encoding, safe sinks, sanitization when HTML is required, CSP as defense-in-depth.

07Template / EL injection+

Interpreter: server-side template or expression engine.

Failure: user input becomes a template or expression, not only a value.

Impact: sensitive data access and potentially server-side execution.

Primary defense: fixed templates, sandboxed engine, no user-authored expressions.

08XPath / XML injection+

Interpreter: XML / XPath query engine.

Failure: input changes a path or predicate.

Impact: filter bypass and XML data disclosure.

Primary defense: parameterized XPath APIs where available, strict schema and encoding.

09CRLF / header injection+

Interpreter: HTTP header parser or log processor.

Failure: carriage return / line feed characters create new fields or records.

Impact: response splitting, cache issues, log forging.

Primary defense: framework header APIs and rejection of control characters.

10Code / eval injection+

Interpreter: language runtime.

Failure: attacker-controlled text reaches eval, reflection, or generated code.

Impact: execution with application privileges.

Primary defense: eliminate dynamic evaluation; map allowed choices to fixed functions.

BEST1. Avoid the interpreter

Use a domain library instead of shell commands or dynamic evaluation.

STRONG2. Parameterize

Separate executable structure from data through a safe API.

REQUIRED3. Validate by allow-list

Constrain type, length, range, format, and permitted values server-side.

CONTEXTUAL4. Encode / sanitize

Encode for the exact output context; sanitize only when rich content is required.

DEPTH5. Limit blast radius

Least-privilege identities, segmentation, CSP, monitoring, and safe errors.

WORKSHOP REFERENCE

Security glossary

Short definitions for the terms used throughout this session.

CWE

A taxonomy of recurring software and hardware weakness types. A CWE describes a root-cause pattern, not one product vulnerability.

CVE

An identifier for a specific publicly disclosed vulnerability in a product or component.

CVSS

A severity framework describing technical characteristics. It is not a complete business-risk score.

EPSS

An estimate of the probability that a published CVE will be exploited in the wild in the next 30 days.

Hardening

Reducing attack surface and configuring a component to an approved security baseline.

Drift

Effective runtime configuration diverging from the intended, reviewed source of truth.

Parameterization

Passing command structure and untrusted data through separate channels so data cannot change command syntax.

Validation

Checking that input matches the expected type, range, length, format, and allowed values. It complements—not replaces—safe construction.

Encoding

Representing data safely for a specific output context such as HTML text, an attribute, a URL, JavaScript, or CSS.

Sanitization

Parsing and removing unsafe parts of rich content when plain context-aware encoding would destroy required markup.

Safe sink

An API that treats input as data in its context, such as textContent for browser text or a parameterized database call.

Policy as code

Versioned, testable rules that automatically accept or reject infrastructure, deployment, or runtime intent.
